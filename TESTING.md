## Lag Safety: Server Input State Gate, Drill Retry, Reopen — 2026-10-04

- Trigger: an independent review reproduced a Search mistake offline: an input stall starting on a step's direction frame makes the server run that direction again after 0.25 s, and with about 300 ms receipts the press reaches the server after the overshoot. 1.0.2 has the same hole for one frame per step; the 0.08 s pre-send widened it to five frames. Reproduced here: 300 ms receipts, 240 ms stall, 40 boards per start frame: 1.0.2 19 mistakes (start +0 only), pre-send 19 (starts +0 to +4).
- First design (input acknowledgement, `rpc_player_input_array_ack`) rejected after the first review: the server acknowledges a frame when it receives it, and after a miss `AuthoritativePlayerInputHandler.update` sets `_parsed_frame = frame - 1` while index 1 still holds the last frame received before the miss (`authoritative_player_input_handler.lua:124-136,153-157`); frames that arrive later but below that frame land at index <= 0 and are never read. The server can therefore keep running an old direction frame while acknowledging newer ones. Driving the real handler: 3 of 120 boards with a wrong press (0.2 s upstream spike at 50 ms receipts); also a wrong press after a resync re-sent a step whose old result was still in flight, and after a reopen timeout on a stale cursor.
- Current gate: the server writes, per tick, its last simulated frame and `had_received_input(frame)` (= frame <= `_received_frame`) into the local player's `server_unit_data_state` game object (`player_unit_data_extension.lua:916-1009`). Network receipt precedes the fixed frames, so true means frame N ran with N <= received, hence any earlier miss has been realigned and N ran its own input; later frames only ever read input from frames >= N (review pass 2 confirmed this against the source, including the skipped-input path, the initial clock, panic and several frames per tick). `BetterBrainer.lua` reads both fields in a safe hook on `_read_server_unit_data_state` (pcall around `GameSession.game_object_field`) and keeps the newest timely frame per input handler (not per unit: the flag comes from the handler, which outlives a respawn). It also records the newest fixed frame whose serialized movement is non-zero, ours or the player's, in or out of a session.
- Search and Drill submit only when the newest timely frame exceeds the last direction frame; a re-press needs a timely frame after the earlier press; Search ends a resynchronization only with that proof. Without any server state on the handler (engine change), a one-second wait after the last direction replaces the proof; once states arrive the wait is never used.
- Drill: a move pending for 2.5 s with a timely frame after it is cleared and retried with direct aim (prediction off for the mission). Without server state the existing uncertain-move exit remains.
- Search reopen: a client session starting off-centre without a recentre since our own `start` (tracked per minigame through `start` and `set_cursor_position`; unknown counts as stale) waits for the exact recentre (3,2). Other cursor receipts during the wait only replace the stale cursor. After the receipt timeout: moves from the shown cursor, no press until a move is confirmed as predicted or a resync settles; on the target it steps off and back. A resync also clears a running hold so no unlisted pre-sent step follows.
- Kill switches (Search pre-send; Drill prediction and holding) re-arm on `gameplay_exit`.
- Offline (`search_spec` 21/21, `drill_spec` 36/36, `speed_spec` 73/73; the fixture reports frame n of tick n + 3 as timely unless a stall substitutes older input, queued behind that frame's RPCs):
  - Search stalls 0.24/0.40 s from each of the first six frames after a stage-2 step, 10 seeds, 50/165/300 ms receipts: 0 mistakes, all solved (300 ms: 1.0.2 6/120 mistakes, pre-send alone 20/120).

  - Reopen off-centre: plain 17, after a settings change 17, on target with receipts stalled 1 s 20 reopens: 0 mistakes (previous version: mistakes in the latter two).
  - Real-handler sweeps (review scripts): upstream +6 to +20 ticks, ramps, 25-40 tick client hitches, downstream stalls with re-sends; Search and Drill at 50-300 ms receipts: 0 mistakes, 0 exits.
  - Cost, no stalls: Search mean solve 1.166 -> 1.271 s (30 ms) and 1.807 -> 1.912 s (165 ms); 1.0.2 1.268/2.189 s. Drill 3.025/3.193 s unchanged; 3.34 -> 3.54 s at 240 ms receipts (the hold lasts until its result).

## Balance Restart And 330-ms RTT

- User reports the dot escaping at approximately 330-ms RTT and after closing/reopening the terminal. Exact game build, mission, server tick rate, packet gaps and process-loaded revision are unknown. No runtime connection or deployment was authorized or performed for this revision.
- Client entry no longer initializes from a possibly retained UI position with zero velocity. Two fresh position RPC samples, separated by at least 1/240 second and no more than 250 ms, seed clamped velocity. A gap over 250 ms requires a new pair. Local authority still samples its position directly. This intentionally leaves native input unchanged while client velocity is unready.
- Local start resets tracking. An argumentless client stop within the original 1.2-second entry window may recover only with exact current local CSM/minigame identity, scanner visible, gameplay active and live terminal. Native stop still runs and clears ownership. Recovery discards all pre-stop estimates/commands and requires two post-stop samples before that deadline; repeated stops do not extend it. Explicit Player/boolean/nil stops and expired recovery block automation until a new start or lifecycle reset. Exit, settings, disable, unload and gameplay exit clear retained state.
- RTT cap is 500 ms rather than 250 ms. Prediction covers 850 ms: capped RTT + maximum accepted sample age (250 ms) + maximum modeled tick (100 ms). At 330-ms RTT and 52 Hz, a fresh sample needs about 349.23 ms of prediction before extra sample age; the old 350-ms horizon left less than 1 ms of slack, even if its RTT cap were raised alone. The 250-ms timeout is a receipt-gap limit, not a ping limit, and remains unchanged.
- History holds 256 commands rather than 48. At the maximum modeled 240 Hz this spans about 1.06 seconds, exceeding the 850-ms horizon; at 52 Hz it spans about 4.90 seconds. Prediction uses at most 205 integration steps, enough for 850 ms at 240 Hz. A single ordered history walk replaces a reverse scan per step, bounding work by history entries plus integration steps rather than their product. Timestamp coalescing preserves command ordering when smoothed RTT falls; repeated input aliases update one history entry, not additional entries. These are static work bounds, not measured live CPU improvements; tick rates outside the existing 10-240 Hz model remain unverified.
